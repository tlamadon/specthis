# specthis — product architecture

**Status: 2026-08-11.** The product-level description, after the
attestation reframe (`attestation-model.md`) and the decision to
delegate **byte production entire** — execution, scheduling and caching —
to a pluggable compute manager. The line falls on **making**, not
**knowing**: specthis still derives and reports what is out of date, it
just never rebuilds anything. Supersedes the part of
`two-trees-and-delegation.md` noted in §9.

---

## 1. What specthis is

**specthis certifies that code implements its specification, compiles
that specification into an executable pipeline, and countersigns what
the machine reports back.**

It never forks a process, never drives a rebuild, and never judges. It
owns one question — *does the code do what the prose says?* — and one
record: a git-versioned ledger of who claimed what, over which digests.

It still *reports* what is out of date on the byte side — that stays
offline and cheap (§10). What it delegates is **making bytes**, not
**knowing about them**.

Everything about *producing bytes* belongs to a compute manager the
user chooses.

---

## 2. The four roles

| Role | Does | Produces |
|---|---|---|
| **Author** | writes the contract in prose (math welcome) | specs |
| **Implementer** | grounds logical names in bytes | code, the map |
| **Judge** | reads code against prose | a vouch |
| **Compute manager** | reproduces the byte chain | artifacts + manifests |

specthis is none of them. It is the notary they all file with, plus the
compiler that turns their declarations into a pipeline.

The judge and the implementer are frequently the *same agent*. That is
acknowledged, not forbidden — see `attestation-model.md` §10.

---

## 3. The artifacts

| Artifact | Written by | Answers |
|---|---|---|
| **specs** | author | what does this entry *mean*? |
| **map** (`bindings.toml`) | implementer | what is it made of, and how does it run? |
| **pipeline** | **generated by specthis** | what steps, with what inputs and outputs? |
| **certificates** | **generated by specthis** | which code identity is this step running? |
| **vouches** | notary, from the judge's attestation | was it judged, at which digests? |
| **manifests** | compute manager | what ran, over which bytes, producing which |
| **runs** | notary, from adopted manifests | the signed provenance archive |

The spec declares the DAG in **logical names**. The map **grounds** it —
code, command, executor, physical output locations. The pipeline is the
**compilation** of the two, and is generated-only: hand-edit it and the
source of truth forks.

---

## 4. The flow

```
   author ─── specs ────┐
                        ├──► specthis compiles ──► pipeline + certificates
implementer ─── map ────┘                                    │
                                                             ▼
                                                     compute manager
                                                    (executes, caches)
                                                             │
                                                          manifests
                                                             │
   judge ──── vouch ──► specthis records ◄──── specthis adopts (signs)
                              │
                              ▼
                    vouches.toml     runs.toml
```

**The arrow is one-way.** Two file handoffs — pipeline down, manifests
up — and **no callbacks**. The compute manager never calls specthis.
That is what lets it run on a cluster where specthis isn't installed,
offline, hours later, from a queue. A convenience call would spend
exactly that property.

---

## 5. What specthis compiles: the pipeline

One step per entry, derived from spec + map:

```
id:      clean-wages            # the entry name — shared vocabulary
command: python src/clean.py    # from map.run
inputs:  [ certificate, config/clean.toml, <upstream outputs> ]
outputs: [ data/wages.parquet ] # from map.produces
deps:    [ raw-wages ]          # from spec.consumes
```

Concretely this is a `dvc.yaml`, a scripthut workflow document, or the
input to a ~300-line reference runner. The compiler is the per-tool
adapter; everything above it is tool-agnostic.

**Entry names are the only shared vocabulary.** No step merging,
splitting, or renaming — adoption is per entry.

---

## 6. Code certificates

specthis emits, per entry, a small file recording **code identity**: the
bound scripts as `{path: sha}`, the package blob digest, and the entry
name. The pipeline declares it as an ordinary input.

The manager hashes it like any other file and understands nothing about
it. Judgment thereby enters the execution chain without the executor
learning a single new concept — the arguments-are-files doctrine applied
to a judgment.

**The keyed content is code identity only.** Not the verdict, not
`spec_sha`. If either entered, vouching something would re-run it and
rewording prose would re-run it — destroying the property that a
clarification costs zero compute.

What the certificate buys, given the code files could simply be listed
as inputs directly:

- **Globs become hashable.** `[package] globs` has no stable file list;
  the certificate is where a composed blob digest becomes a real input.
- **Compactness.** Forty source files as inputs on every step is noise;
  one certificate keeps the pipeline readable.
- **The provenance link.** The manifest records the certificate's digest;
  the certificate's digests are the key into `vouches.toml`. So *"was
  figure 3 produced by certified code?"* is answerable from the manifest
  chain alone — recorded by a tool with no idea what a vouch is.

## 7. What the compute manager must guarantee

**MUST — or the claims become lies:**

1. **Honor declared dependency order.** Never start a step before its
   dependencies succeeded.
2. **Decide only on content.** Under a delegated pipeline, deciding what
   to run *is* the manager's job — but the decision must be a function
   of content digests over the declared inputs, and nothing else. **No
   mtimes, no timestamp heuristics, no "looks recent."** Deciding on the
   wrong evidence is what breaks the claims; deciding is fine.
3. **Emit a per-step manifest** — input hashes *as used*, output paths +
   content hashes, exit code. Distinguish *not hashed* from *empty*.
4. **Never reuse a failed result.**
5. **Make cache hits invisible** — identical hashes on hit and miss.
6. **Preserve entry ↔ step identity.**
7. **Land outputs where declared.**

**SHOULD:** exclude resources from the cache key; offer a side-effect-free
probe; fail loudly on unverifiable inputs; avoid leaving partial outputs;
keep logs addressable per step.

**MUST NOT:** write specthis's ledgers; edit the map.

**Needs to know nothing about:** specs, prose, vouches, contracts,
judgment, or certification. It receives steps with declared inputs,
outputs and edges, and reports what it did.

**Candidates**, per the 2026-07-20 assessment: **scripthut** (fits;
`cache_scope: "inputs"`, `task probe`, local backend, and
`manifest_version: 1` all shipped), **DVC** (satisfies the semantics;
brings workspace-linking opinions), the **reference runner** (proof the
contract is complete). **dud does not qualify** — no rebuild on command
change, manual commit; it fails at the semantic clause, not the plumbing.

## 8. Adopt: countersigning

A manifest is an *unsigned factual report* from a machine. **Adopt is
the notary act**: specthis verifies it, records it in `runs.toml`, and
the repo now carries the claim.

Why record rather than merely read:

- **Self-contained repo.** The paper's repository holds the claim that
  figure 3 came from those bytes — the product's leading promise.
- **Durability.** The manager's store gets pruned, the service goes
  away, the cache is cleared. A committed record outlives all of it.
- **Portability.** A referee clones the repo and sees the claims without
  access to your cluster.

`runs.toml` changes role: it stops **driving execution** and becomes the
**provenance archive** — plus the recorded table specthis still compares
against when *reporting* currency (§10). What left is its authority over
rebuilds, not its use.

A read-only mode — verify the manifest chain without recording — is a
legitimate lightweight variant for CI.

## 9. What stays, what leaves

**The line is execution, not derivation.** specthis keeps knowing; it
stops making.

**Stays:** spec parsing and digests; the map; the two-table comparison
on *both* axes — certification and currency reporting alike;
propagation on both trees; `expected_inputs` (still the implied table
for reporting); `runs.toml`; adopt; the pipeline compiler; certificates;
the dashboard.

**Leaves:**

| Leaving | Why |
|---|---|
| executor, dispatch, parallel scheduler | the manager's job |
| `run --stale` as a *builder* | becomes compile → submit → adopt |
| the composed run `signature` | vestigial once tables are authoritative |
| specthis's remote cache | redundant against a caching backend |
| the fused status word | a 2D→1D projection nobody can read |

`run --stale` survives as UX, now thin: **compile → submit → adopt.**

**This supersedes:** `two-trees-and-delegation.md` §14's
scripthut-specific framing, which becomes one instance of a pluggable
contract. `attestation-model.md` is otherwise **unchanged and
reaffirmed** — §5's one engine still runs on both axes, and §12's
findings all still apply, because derivation never left.

**Unchanged:** the pure-contract spec format; the blast-radius dial;
arguments-are-files; the deferred template tier; and the complexity
budget — still **one engine**, the two-table comparison, applied twice
with different pinned tuples. Delegation removed machinery without
touching it.

## 10. Two questions this settles

**Do specthis and the manager both need the whole pipeline?** Yes — and
that is not duplication, because **only one authors it.** The source of
truth is spec + map; the pipeline is a build product. Both parties read
it; exactly one writes it.

**Who answers what about bytes?** Three questions, not two, and only the
third needs the tool:

- **Currency** — *have the inputs moved since the recorded run?* →
  **specthis, offline.** It generated the pipeline, so it knows the
  declared inputs; it rehashes local files, takes each non-local
  upstream from that upstream's *recorded* `output_sha` (the claim, not
  the bytes), and compares against the adopted manifest. Same two-table
  diff as certification.
- **Integrity** — *are the recorded outputs still the bytes claimed?* →
  **specthis, offline.** Rehash the declared outputs against the
  manifest. Absent bytes are not edited bytes: the claim stands
  unmaterialized.
- **Cost** — *is fixing this a cache restore or a real compute?* → **the
  manager's probe.** Only the tool knows its own store.

**`check` therefore stays a pure function, both axes.** The tool is
needed for cost, never for truth.

**And the two currency notions coincide by construction.** Because
specthis generates the pipeline, both parties hash the same declared
input set. The only possible divergences are the command string (in the
tool's key, not specthis's) and the git commit (in scripthut's key
unless `cache_scope: "inputs"`). Set that flag, keep the command
information-free per arguments-are-files, and the answers are identical
— one computation performed in two places for two purposes, not two
engines that can disagree.

---

## 11. Open

- **Which adapter first.** scripthut (its side is done) then the
  reference runner — two backends with no shared lineage is what proves
  the contract is real, and far cheaper than a DVC integration.
- **Certificate format and location** — committed, or generated into an
  ignored directory? Committed makes the repo self-contained; generated
  avoids churn.
- **Whether `runs.toml` becomes append-only** now that it is an archive
  rather than a decision input. The argument for it strengthens.
- **How independence is declared** per entry (`attestation-model.md` §10).
- **The template tier**, still deferred behind its own trigger. Note the
  payoff under this architecture: a 12-cell grid stays one spec entry,
  one map row, one vouch, one certificate — and twelve pipeline steps,
  all machine-generated.
